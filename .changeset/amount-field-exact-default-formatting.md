`AmountField`: the default mode now formats on blur and on the arrow keys without floating-point math.

Behaviour change: in the default mode (`formatOnBlur` omitted or `true`), the text and the form value keep every digit the user typed, padded or rounded half away from zero to `decimals`. `0.1` at 18 decimals gives `0.100000000000000000` (was `0.100000000000000006`), `1.005` at 2 decimals gives `1.01` (was `1.00`), and integers past 2^53 are no longer altered or put in exponent form. Arrow-key steps are exact too: `0.1` plus a `step` of `0.01` at 18 decimals gives `0.110000000000000000`. A zero result never has a minus sign (`-0.001` at 2 decimals gives `0.00`). A value written from outside the field that is not a plain decimal is no longer rewritten on blur or stepped by the arrow keys: text such as `1,000`, `12abc`, `1e3` or ` 1.5` (with surrounding spaces) stays as it is, and so does a number value that does not display as a plain decimal, so `1e21` is no longer rewritten to the string `1e+21` on blur and a `NaN` or `Infinity` value no longer steps from `0`. Existing validation still runs on these values as before. An arrow key with a `step` that is `NaN` or infinite now writes nothing, and a `min` or `max` that is `NaN` or infinite is ignored instead of writing `NaN`. A `decimals` value that is not a whole number from 0 to 100 now leaves the text unformatted instead of formatting to a coerced number of decimals or throwing, and the field is still marked as touched on blur. Forms built by the renderer show the exact text but still convert the value to a number when submitted.
